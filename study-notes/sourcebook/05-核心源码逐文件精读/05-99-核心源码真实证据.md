# 05-99 核心源码真实证据卷

> 本卷只引用当前 `jimi-code` 的真实入口和调用关系。Java 与 Go 是两套实现；除非明确标注，不把一套实现的字段或错误传播推断到另一套。

## 1. Java 启动文件 `src/main/java/com/mewcode/MewCode.java`

`main` 的第一段只处理配置路径：命令行第一个参数优先，其次读取 `MEWCODE_CONFIG`，没有时让 `ConfigLoader` 自己按用户目录和当前目录查找。第二段调用 `ConfigLoader.load`，只捕获 `ConfigLoader.ConfigException`；配置失败打印 `Configuration error` 并以状态码 1 退出。第三段创建 `MewCodeModel`，把 provider、MCP server 和 hook 列表注入，而不是在 Agent 内部重新读取 YAML。第四段创建 TUI4J `Program`，把 program 反向注入 model，以便 model 在运行中发送命令。第五段隐藏光标、注册延迟 SIGINT handler、运行 program，finally 中恢复光标。

学习断点应放在 `ConfigLoader.load` 返回、`new MewCodeModel`、`new Program`、`program.run` 和 finally。配置异常发生在 UI 创建前；模型异常发生在 UI 已运行后；SIGINT 不是 Java Exception，而是 signal 回调调用 `model.handleSigint`。终端光标恢复属于 finally 副作用，即使 TUI 抛异常也应执行。

## 2. 配置文件 `src/main/java/com/mewcode/config/ConfigLoader.java`

`load(String path)` 有显式路径分支和分层合并分支。显式路径只读一个 YAML 并校验；默认分支依次访问 `user.home/.mewcode/config.yaml`、`user.dir/.mewcode/config.yaml`、`config.local.yaml`，后读层通过 `mergeConfig` 覆盖前读层。`loadSingleFile` 使用 SnakeYAML `Constructor(AppConfig.class)` 和 `SnakeCasePropertyUtils`，因此 YAML 的 snake_case 可以绑定 Java 属性。空文件转换为空 `AppConfig`，文件不存在、读取异常和解析异常都包装为 `ConfigException`。

阅读时特别确认：配置层是合并还是替换；providers 为空列表时是否覆盖；环境变量是在 `ProviderConfig.resolvedApiKey` 读取，而不是 ConfigLoader 读取；错误是否在启动期抛出。测试应覆盖不存在文件、非法 YAML、未知 protocol、Key 缺失和多层覆盖。

## 3. Agent `src/main/java/com/mewcode/agent/Agent.java`

Agent 持有 LlmClient、ToolRegistry、protocol、contextWindow、maxOutput、PermissionChecker、HookEngine、maxIterations、workDir、sessionId、通知函数、toolNameFilter、instructions、memoryContent、replacementState、recoveryState 和 fileHistory。字段表说明它不是无状态函数：会话、压缩、工具结果替换和恢复都跨 iteration 保存。

一次循环的真实顺序是：根据 `toolNameFilter` 取得可见 schema；把 instructions、memory、plan mode 和 conversation 交给 client；消费 `StreamEvent`；将 thinking/text 写入 assistant message；收到 tool use 后解析参数；调用 PermissionChecker；如果允许，执行 Tool；把输出通过 ToolResultBudget 截断或替换；追加 ToolResultBlock；若工具触发 compact、skill、subagent 或退出命令，则更新 Agent 状态；没有 tool call 时发送 LoopComplete。`MAX_OUTPUT_RECOVERIES=3` 表明输出过长或上下文失败不是无限重试。

写工具成功后模型再次失败，不代表文件或远端副作用回滚。恢复只能依赖 FileHistory、Session、Worktree 或业务查询。测试应固定 fake LlmClient，使它先返回 tool call、再返回错误，观察 tool result 是否被保存以及下一次恢复是否重复执行。

## 4. LLM 适配器

`LlmClient.create` 根据 protocol 选择 Anthropic、OpenAI、OpenAI-compatible 实现。`AnthropicClient` 和 `OpenAiClient` 都检查 `resolvedApiKey`，创建官方 SDK，保存 model/systemPrompt/thinking/maxOutputTokens，并在虚拟线程中把 SDK stream 转成 `BlockingQueue<StreamEvent>`。队列容量 64 是背压边界；生产者异常被转换为 Error event，消费者必须处理 Error 和终止。

Anthropic 的 content block 和 OpenAI Responses event 不同，尤其是 thinking 签名、tool call input 增量、finish reason 和 usage。项目统一到 StreamEvent 是适配层，不是供应商语义完全相同。`LlmException.AuthenticationException`、`RateLimitException`、`ContextTooLongException`、`NetworkException` 的处理建议不同：认证修配置，限流退避，上下文压缩，网络错误先查询请求是否已被接受。

## 5. ToolRegistry 与 PermissionChecker

Registry 的 `Register`、`Get`、`ListTools` 和 deferred tool discovery 只回答“工具能否找到”。PermissionChecker 还要检查 mode、tool category、计划模式允许集合、content field、路径规则、危险 shell pattern 和 YAML permissions。`SAFE_COMMANDS` 是保守 allowlist；危险正则覆盖根目录删除、mkfs、dd、chmod 777、fork bomb 和下载后管道执行。

真实链路是 `Agent -> Registry.Get -> PermissionChecker.check -> Tool.execute`。任何一个环节失败都要保留 tool name、参数摘要、mode、projectRoot 和拒绝原因。不能因为模型反复输出同一 tool call 就跳过检查。

## 6. McpManager

`connectAll` 对配置逐个创建 transport，调用 initialize、读取 instructions、listTools，再用 `McpToolWrapper` 将 SDK tool 转成内部 Tool。单个 server 失败写入 `ConnectResult.errors`；成功的 server 仍提供 tools。`shutdown` 关闭所有 client。MCP 工具拥有网络或外部进程副作用，Schema 只是参数契约，仍需权限、超时和审计。

## 7. ContextCompactor、Session 与 Worktree

ContextCompactor 先根据真实 usage anchor 或字符估算判断阈值，再做工具结果预算替换；仍超限时请求摘要，并写 `compact_boundary`。RecoveryState 保存最近文件读取与技能调用，用于恢复后的环境重建。SessionManager/HistoryStore 保存消息和 boundary；FileHistory 保存编辑备份；WorktreeManager 隔离 Git 文件但不隔离 LLM/MCP 副作用。

## 8. Go 对照证据

Go `cmd/mewcode/main.go` 处理 teammate flag、`config.LoadConfig`、hook 校验和 Bubble Tea；`internal/agent/agent.go` 的字段与 Java Agent 对应，但使用 context、channel 和函数回调；`internal/llm/client.go` 返回事件 channel/error channel；`internal/tools/tool.go` 定义 Tool、Registry、DeferrableTool 和 SystemTool；`internal/permissions` 承担安全决策。对照实验必须分别运行 `go test ./...` 和 Gradle/Maven 测试。

## 9. 真实故障实验

1. 删除 Key：验证 client 构造错误与 TUI 退出。
2. 让模型返回 context-too-long：验证 compaction 和 boundary。
3. 让工具写入后返回错误：验证 FileHistory 和重复风险。
4. 让 MCP Server command 不存在：验证部分连接错误。
5. 在 SubAgent 使用 Worktree 后中断父进程：核对 mailbox、session 和未提交变更。
6. Ctrl+C：确认光标恢复、队列停止和 session 可读。

## 10. 当前事实/原理/建议

当前事实来自上面的真实类和字段；原理是 Agent Loop、队列、权限、压缩和 Git 隔离如何协作；生产建议包括沙箱、租户审计、工具幂等、外部副作用查询、统一错误事件、MCP 认证和共享恢复存储。不能把建议写成 MewCode 已经默认具备的能力。

## 11. 文件级精读展开模板

对 `AppConfig.java`，先列出 providers、mcpServers、hooks 字段和 getter/setter，再追 ConfigLoader 的合并策略，最后观察 MewCodeModel 如何消费它。对 `ProviderConfig.java`，记录 protocol、baseUrl、apiKey、model、thinking、contextWindow、maxOutputTokens 的默认值、环境变量解析和校验。对 `McpServerConfig.java`，列 command、args、env、url 和 transport 的互斥关系，说明 Windows 与 Unix 的启动差异。对 `HookConfig.java`，列事件、条件、动作、reject 字段，并追 HookEngine 如何把 YAML 变成 HookContext。

对 `ConversationManager.java`，逐个记录 addUser、addAssistant、addThinking、addToolUse、addToolResult、getMessages、clear 和序列化方法；重点检查 tool id 是否配对、thinking signature 是否丢失、消息顺序是否能被 Anthropic/OpenAI 两个适配器共同理解。对 `SessionManager.java`，记录 session 文件命名、追加写入、边界扫描、消息统计和 resume 读取；如果写入失败，确认内存 conversation 是否仍继续，避免把“磁盘记录失败”误当成“模型调用失败”。

对 `ToolResultBudget.java`，记录完整输出、截断输出、替换记录和 token/字符估算；对 `ContentReplacementState.java`，记录每个 tool result 的决策是否跨 iteration 固定，为什么稳定前缀有利于 prompt cache。对 `ContextCompactor.java`，记录阈值、摘要 prompt、保留 tail、RecoveryState 消费、compact_boundary 写入和失败恢复。对 `RecoveryState.java`，记录按 path/name 覆盖旧快照的行为，以及恢复时文件已经变化的风险。

对 `FileHistory.java`，记录备份目录、版本号、时间戳、快照和恢复方法；写文件成功但备份失败时是否继续，是必须通过源码和测试确认的事实。对 `WorktreeSession.java`、`AgentWorktree.java`、`WorktreeManager.java`，记录 worktree 路径、分支/提交、变更摘要、清理条件和 stale 检查；不要把 worktree 清理理解为任意目录删除，它必须先检查未提交变更和 active session。

对 `MewCodeModel.java`，逐个记录 TUI 消息类型、输入框状态、当前 Agent、队列消费、spinner、Markdown 渲染、permission dialog、plan dialog、subagent progress 和退出信号。UI 事件线程与 Agent/LLM 虚拟线程不是同一线程，更新状态必须经过 TUI 的消息机制。客户端关闭终端时，模型请求可能仍在运行；调试要看 cancellation flag、queue producer 和 program quit 的顺序。

## 12. Go 文件的独立精读

`internal/config` 的 Config 结构、默认路径和合并方式要单独记录，不要直接套 Java。`internal/llm` 的 `Client.Stream` 用 context 控制取消，并返回事件 channel 与 error channel；消费方必须同时 select 两个 channel，否则错误可能被遗忘。`internal/tools` 的 Registry map 没有 Java synchronized 语义，若 team 并发注册或查找工具，需要检查调用线程。`internal/worktree` 和 `internal/session` 的文件锁、错误返回和清理方式也不能用 Java 异常模型替代。

## 13. 每个 public 方法的验收问题

1. 参数为空、路径不存在、配置缺失时返回什么？
2. 方法是否读写文件、启动进程、访问网络、修改 Git 或写 session？
3. 方法是否可能阻塞，是否运行在虚拟线程/goroutine/TUI 线程？
4. 错误是抛异常、返回 Result、写 Error event，还是静默降级？
5. 调用者是否会重试？重试会不会重复副作用？
6. 方法后续由哪个状态机或事件继续？
7. 测试是否覆盖成功、失败、取消、重复和恢复？

## 14. 推荐的逐文件学习顺序

先读入口与配置，再读接口和数据模型，再读一个最小工具，接着读 Agent Loop，之后读 LLM 适配器和权限，最后读压缩、会话、MCP、SubAgent、Team 与 Worktree。每完成一层，就用 fake provider 验证，不要等所有文件读完才第一次运行。对 206 个 Java、99 个 Go 生产文件，按包拆分，每次只处理一个边界，避免把模板概述误当成逐文件完成。

## 15. 逐文件补充：入口、配置、状态和副作用四联表

阅读 `MewCode.java` 时，入口是 `main(String[])`，配置副作用是读取文件和环境变量，状态副作用是创建 TUI model，外部副作用是注册信号和启动 UI。阅读 `ConfigLoader.java` 时，入口是 `load`，配置状态是合并后的 `AppConfig`，副作用是文件读取，错误副作用是抛出 `ConfigException`。阅读 `Agent.java` 时，入口是 run/loop 方法，状态是 Conversation、replacement state、recovery state 和 compact tracking，外部副作用是 LLM、工具、文件、命令、MCP 和 session。阅读 `PermissionChecker.java` 时，入口是 check，状态是 mode/rules，副作用是允许或拒绝；它本身不执行工具。

阅读 `LlmClient` 时，入口是 stream，状态是队列和 provider 请求，外部副作用是网络和 token 计费；阅读 `ToolRegistry` 时，入口是 register/get/list，状态是工具 map/discovered map，副作用主要是 schema 可见性；阅读 `McpManager` 时，入口是 connectAll/registerAllTools/shutdown，状态是 configs/clients，副作用是启动进程或建立 HTTP 连接。阅读 `ConversationManager` 时，入口是消息追加和读取，状态是内存列表，副作用是序列化或交给 Session；阅读 `ContextCompactor` 时，入口是 compact decision，状态是 summary、tail、RecoveryState 和 boundary，副作用是摘要模型和 session 写入。

这四联表可以复制到每个普通文件：先找入口，再找字段状态，再找外部副作用，最后找异常和验证。对 Go 文件，把“方法”换成函数/方法，把“队列”换成 channel，把“异常”换成 error 返回和 context cancellation。对资源文件，把入口换成加载方，把状态换成绑定对象，把副作用换成构建、启动或文件写入。

## 16. 复刻项目的最小契约

一个可学习的 mini agent 不需要复制全部 UI。它至少要拥有 Config、Message、ModelClient、Tool、Permission、Session 六个接口。ModelClient 接受消息和工具 schema，返回确定性的 fake events；Tool 接受结构化 args 和 Context，返回 output/isError；Permission 在执行前返回 allow/deny；Session 追加消息和 boundary。先用内存实现，再把 Session 换成 JSONL，最后接真实 SDK。

复刻验收要覆盖：普通回答只产生 text/complete；工具回答产生 tool use、permission、tool result、第二轮 text；权限拒绝不会执行工具；模型超时返回结构化 error；输出过长进入 compact；进程重启后能从 session 读取消息；MCP 工具注册失败不会清空内置工具。只有这些契约稳定后，才值得加入 SubAgent、Team 和 Worktree。

## 17. 面试回答结构

介绍项目时先说它是终端 AI coding agent，再说 Java/Go 双实现和 Maven 独立变体；介绍 Agent 时说消息循环、工具调用、权限、压缩和恢复；介绍安全时说 schema 与授权分离、命令/路径 allowlist、MCP 外部进程和审计；介绍稳定性时说队列背压、超时、取消、session boundary、FileHistory 和 Worktree；介绍工程亮点时给出真实类名、故障场景和验证证据。不要只说“接入了大模型”。

## 18. 最终复盘

每次源码学习结束，把一条成功调用和一条失败调用并排记录：入口文件、调用方法、状态变化、事件顺序、外部副作用、恢复方式和生产建议。无法确认的部分标记未实测；第三方 SDK 内部实现不可取得时标记 source-unavailable。这样教材既能帮助新手复刻，也不会把静态推断误写成当前运行事实。
